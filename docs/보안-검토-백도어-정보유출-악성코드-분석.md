# 보안 검토: 백도어 · 정보 유출 · 악성코드 가능성 분석

> 작성일: 2026-11-04
> 대상: ARTEX (상류 `Autumn-27/artex`의 fork), 분석 브랜치 `i18n/korean`
> 동기: 중국산 오픈소스 프로젝트를 운영 투입하기 전, 은닉 백도어 / 무단 데이터
> 외부 전송 / 악성 코드 존재 여부 확인
> 성격: **정적 소스 코드 감사(이 git 트리 한정)**

## 0. 결론 요약

이 저장소 트리의 Go/TS/JS/설정 소스를 전수 점검한 결과,
**은닉 백도어 · 몰래 하는 정보 유출 · 난독화된 악성 페이로드는 발견되지 않았다.**
오히려 SSRF 방어, 알림 비컨 차단, 업데이트 출처 하드코딩, 시크릿 마스킹 등
**방어적으로 신중하게 작성된 흔적**이 다수 확인된다.

단, "외부에서 코드/데이터가 오가는" 신뢰상 구조적 지점 2가지는 악성이 아니더라도
운영자가 반드시 인지하고 통제해야 한다(§2).

## 1. 영역별 점검 결과 (이상 없음)

### 1.1 외부 통신 (egress)
비(非)테스트 코드의 하드코딩 URL/IP를 전수 확인. 모두 정당한 용도:

- GitHub(`api.github.com` 등): 자가 업데이트 전용 (§2.1)
- 사용자 설정 알림 채널: dingtalk / feishu / wecom / telegram / webhook / email
  — 사용자가 직접 URL·토큰을 넣어야 동작, 미설정 시 전송 없음
- LLM 공급자: `api.openai.com` / `api.anthropic.com` (설정에서 변경 가능, 자체 호스팅 지정 가능)
- 사용자 설정 검색/ASM 연동: brave / tavily / ScopeSentry(MCP, URL·API키 사용자 입력)

> 참고: `traffic/traffic.go:2012`에 보이는 공인 IP `107.172.96.177:8082`는 실제 연결이
> 아니라 `traffic_search` 툴 **설명 문자열의 사용 예시**다(LLM에게 host 필터 사용법 안내).

테스트 파일에는 `example.com`, `attacker.tld`, `169.254.169.254` 등이 많으나, 이는
대부분 **SSRF/마스킹 방어를 검증하는 보안 테스트**로 오히려 긍정 신호다.

### 1.2 텔레메트리 / 추적
analytics·sentry·mixpanel·posthog·google-analytics·beacon 등 **사용 데이터를
외부로 보내는 코드 없음.** 프런트엔드는 정적 익스포트 + 자체 호스팅이라 원격 추적
스크립트를 로드하지 않는다.

> `notify/markdown.go:33`은 오히려 **방어 코드**: 알림 렌더링 시 마크다운 이미지
> `![](http://attacker.tld/beacon)`가 비컨으로 새나가지 않도록 이스케이프한다.

### 1.3 난독화 / 악성 페이로드
base64·hex 디코드는 전부 정상 용도(웹훅 HMAC 서명, 이메일 MIME 인코딩, 페이지네이션
커서, 해시 검증). `eval()` / `Function()` / 동적 코드 삽입 / `\x..` 바이너리 블롭 **없음.**

### 1.4 빌드 / 설치 훅
`web/package.json`의 스크립트는 `prepare: husky`(표준 git 훅)뿐. 설치 시 네트워크에서
무언가 받아 실행하는 postinstall/preinstall 훅 **없음.** 네트워크성 `go:generate` 없음.

### 1.5 인증 백도어
하드코딩된 마스터키/매직 토큰/인증 우회 **없음.** 인증은 JWT 기반(`golang-jwt/jwt`).
코드에서 다수 발견되는 `permission.ModeBypass`는 **에이전트의 툴 권한 모드**(planner/
worker가 매 툴 호출마다 사람 승인 없이 실행하는 자율 모드)이지, 로그인/인증 우회가 아니다.

### 1.6 코드 실행 경로 (`exec.Command` 2곳)
- `selfupdate/bootstrap.go:184` — 새로 스테이징한 바이너리의 스모크 테스트(`<bin> -h`)
- `server/customtool.go:398` — **사용자가 직접 정의해 DB에 저장한** 커스텀 툴의 Python
  코드를 실행. 원격에서 코드를 수신해 실행하는 경로가 아니다.

> ARTEX 자체가 kali 도구를 bash로 실행하는 자율 침투 테스트 플랫폼이므로 "명령/코드
> 실행" 능력은 설계 목적 그 자체다. 이는 백도어가 아니라 제품의 본질이다.

### 1.7 의존성
`go.mod` 직접 의존성은 모두 평판 있는 패키지: `golang-jwt/jwt`(인증),
`jackc/pgx`(PostgreSQL), `lqqyt2423/go-mitmproxy`(트래픽 프록시=설계상 당연),
`miekg/dns`·`projectdiscovery/*`(dnsx/cdncheck 등 정찰 도구=펜테스트 특성상 당연),
`modernc.org/sqlite`, `bluemonday`(HTML 새니타이저=방어적), `golang.org/x/*`.
`go.sum`으로 모듈 무결성 핀 고정됨.

## 2. 인지·통제가 필요한 신뢰 구조상 지점 (악성 아님)

### 2.1 자가 업데이트는 상류(원작자) 저장소를 바라본다

`selfupdate/github.go:15`:
```go
const Repo = "Autumn-27/artex"   // 당신 fork가 아니라 원작자 저장소 (하드코딩)
```

**설계 자체는 매우 안전**하다:
- 업데이트 출처를 설정 불가하게 하드코딩(설정 가능하면 RCE 통로가 된다고 코드 주석에 명시)
- HTTPS 강제, GitHub 도메인 화이트리스트, 리다이렉트 홉 검증(DNS 오염/MITM 방지)
- 다운로드 zip을 릴리스의 `SHA256SUMS`와 대조, 압축 해제 후 스모크 테스트
- 기본 Transport 미재사용(다른 곳의 `InsecureSkipVerify` 영향 차단)

**그러나 신뢰상의 한계**: 검증에 쓰는 zip과 `SHA256SUMS`가 **둘 다 같은 원작자
릴리스**에서 온다. 즉 체크섬은 **전송 중 변조(MITM)·손상은 막지만, 원작자가
악의적이거나 그 GitHub 계정이 침해되면 막지 못한다**(독립 공개키 기반 코드 서명 부재).
이는 대다수 OSS 자동 업데이터의 공통 한계이기도 하다.

**트리거 방식** (코드 확인):
- **버전 확인 = 자동** — 상단 바 배지(`update-badge.tsx`)와 설정 카드가 페이지 로드 시
  `useEffect`로 1회 `GET /api/update/check` 호출. GitHub에서 **버전 번호·릴리스 노트만**
  수신하며, 사용자 데이터는 **일절 전송하지 않음.** 백엔드가 30분 캐시, 실패는 무음 처리.
  개발/소스 빌드는 버전 비교 불가로 배지 자체가 뜨지 않음.
- **다운로드·설치 = 수동 승인 필수** — 설정 「버전과 업데이트」 카드에서 버튼 클릭 →
  `window.confirm()` 대화상자 승인(`update-card.tsx:136`) → `POST /api/update/apply`.
  타이머 자동 설치·백그라운드 무음 다운로드 경로 **없음**(백엔드에 apply 자동 호출
  스케줄러 부재 확인).

| 동작 | 자동 여부 | 내보내는 데이터 |
|---|---|---|
| 새 버전 **확인** | 페이지 로드 시 자동 | 없음 (버전 정보만 수신) |
| 릴리스 **다운로드·설치** | 사용자 버튼 클릭 + 확인창 승인 시에만 | — |

### 2.2 에이전트 프레임워크 `norma`는 같은 작성자의 별도 저장소

`go.mod`: `github.com/Autumn-27/norma v0.4.3`. LLM 호출·툴 실행·권한·압축 등
**에이전트 핵심 로직이 이 모듈에 있다.** 즉 가장 깊은 신뢰가 이 모듈로 이어진다.
버전 핀 + `go.sum`으로 "받은 모듈이 변조 안 됨"은 보장되나, **모듈 코드 자체는 이번
감사 범위에 없다**(저장소 트리에 없고 Go 모듈 캐시에 존재).

### 2.3 설계상 데이터가 외부로 나가는 경로 (사용자 제어 하)

ARTEX는 본질적으로 타깃 정보·캡처된 트래픽·발견 사항을 **사용자가 설정한 LLM
공급자**로 보낸다(자율 분석을 위해). 이는 백도어가 아니라 제품의 동작 원리이며,
**전송처는 사용자가 설정에서 통제**한다(자체 호스팅 LLM 지정 가능). 알림 채널(§1.1)
역시 사용자가 설정한 곳으로만 발견 사항을 전송한다.

## 3. 본 점검의 한계 (투명성)

- **포함**: 이 git 트리의 Go/TS/JS/설정 소스 전수 정적 분석.
- **미포함**:
  1. `github.com/Autumn-27/norma` 의존 모듈의 소스
  2. 컴파일된 바이너리/릴리스 zip 자체
  3. 런타임 동적 행위(실제 네트워크 캡처)
- **최종 확증 방법(권고)**: `norma` 소스를 별도 감사하고, 격리망에서 바이너리를 실행한
  뒤 `tcpdump`/방화벽 egress 로그로 "GitHub·설정한 LLM·설정한 알림 채널 외의 통신이
  있는가"를 1회 실측한다.

## 4. 실무 권고

1. **소스에서 직접 빌드**해 운영 → 자가 업데이트 경로와 배포 바이너리 신뢰 문제를 동시 제거
   (개발/소스 빌드는 원클릭 업데이트가 자동 비활성화됨).
2. LLM은 가능하면 **자체 호스팅/신뢰하는 게이트웨이**로 지정 → 스캔 데이터 전송처 통제.
3. 운영을 **egress 화이트리스트 방화벽** 뒤에 배치(GitHub API·설정한 LLM·설정한 알림
   채널만 허용) → 미지의 통신이 있어도 차단·탐지 가능.
4. 자가 업데이트는 **수동으로만** 수행, 불필요하면 사용하지 않음.

## 5. 재현 / 재점검에 쓴 주요 단서

- 하드코딩 URL/IP 스캔: `*.go`에서 `https?://…` 전수 추출 → 비테스트만 선별
- 코드 실행: `exec.Command` / `os/exec` → 2곳
- 설치 훅: `package.json`의 `postinstall|preinstall|prepare`
- 난독화: `base64.|hex.Decode|eval(|Function(|\x..` 스캔
- 텔레메트리: `telemetry|analytics|sentry|beacon|gtag|posthog|…` 스캔
- 인증 백도어: `backdoor|master.?key|magic|bypass|hardcod|token ==` 스캔
- 자가 업데이트: `selfupdate/github.go`, `selfupdate/stage.go`, `server/update.go`,
